# eBrake

Мобильный мини-HandBrake: перекодирование видео прямо на телефоне, через
ffmpeg, без загрузки на компьютер и без интернета.

Три экрана, свайп между ними, парящий док-бар внизу:

| Ввод | Правка | Вывод |
|------|--------|-------|
| Галерея роликов: превью, группировка по датам, мультивыбор, выбор папки | Движок кодирования и сравнение трёх уровней качества на реальном 10-секундном отрезке | Очередь, прогресс, выполненные задания и экономия места |

## Возможности

- **Сравнение качества на настоящем файле.** Три уровня (Высокое / Баланс / Эко)
  кодируются из 10-секундного отрезка в середине ролика, результат играется
  в плеере с переключением уровня на лету. Никаких «примерных» цифр.
- **Движки в сетке.** Аппаратные кодеки MediaCodec (H.264 / H.265) и программные
  (x264, MPEG-4). Недоступные в конкретной сборке ffmpeg помечены и при сравнении
  автоматически подменяются доступным.
- **Импорт пачкой.** Отметьте несколько роликов в галерее: первый пойдёт на
  сравнение, остальные — сразу в очередь с выбранным уровнем качества.
- **Папка ввода.** Укажите каталог (например, только Downloads) — галерея
  покажет ровно его содержимое, и разрешение на доступ к галерее не нужно.
- **Выполненная очередь.** Сколько роликов пережато, во сколько обошлось и
  сколько места сэкономили (было → стало, с процентом).
- **Кодирование в фоне.** Foreground-сервис с уведомлением: прогресс и кнопка
  «Стоп» есть, даже если свернуть приложение.
- **Папка вывода.** App-specific по умолчанию, либо любая папка хранилища.
- **Журнал.** Полный лог ffmpeg по кнопке, с копированием в буфер.

## Требования

| | |
|---|---|
| Android | 7.0 (API 24) и выше, **только arm64-v8a** (современные телефоны) |
| Размер APK | ~31 МБ (внутри — ffmpeg с кодеками) |
| Интернет | не нужен, всё локально |
| Разрешения | доступ к видео (или папка вместо него), уведомления, foreground service |

## Установка

Готовые APK лежат в [Releases](https://github.com/imd4n/ebrake/releases):

1. Откройте раздел **Releases** и скачайте `eBrake-<версия>.apk`.
2. Положите файл на телефон.
3. Разрешите установку из этого источника (обычно «Настройки → Безопасность →
   Установка неизвестных приложений»).
4. Откройте APK и установите.

> Первая установка из APK всегда требует разрешения «неизвестных источников».
> Обновления приходят тем же путём: скачали новую версию, поставили поверх.

## Сборка из исходников

Нужны **JDK 21** и Android SDK (compileSdk 36.1). Android Studio подойдёт —
достаточно открыть папку проекта.

```bash
# Отладочная сборка → app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:assembleDebug

# Релизная сборка → app/build/outputs/apk/release/app-release.apk
./gradlew :app:assembleRelease

# Юнит-тесты (экономия, формат размеров) — CI гоняет их перед сборкой
./gradlew :app:testDebugUnitTest

# Статический анализ
./gradlew :app:lint
```

### Про ffmpeg

Зависимость `com.arthenica:ffmpeg-kit-next:9.0.0` **не публикуется в Maven**,
поэтому собранный AAR лежит в репозитории: `prebuilt/bundle-android-aar-24-maven/`.
Из-за этого клонирование тянет ~8.5 МБ — иначе сборка упадёт.

Что внутри AAR: `h264_mediacodec`, `hevc_mediacodec`, `libx264`, `mpeg4`, только
arm64-v8a. Собран с `--enable-gpl` (из-за x264) и `--enable-lib-android-media-codec`.
Как пересобрать движок — [docs/FFMPEG_KIT_NEXT.md](docs/FFMPEG_KIT_NEXT.md).

## Релизы и подпись

Релиз = тег вида `v0.1.0`. Workflow `.github/workflows/release.yml` по пушу тега
собирает APK и вешает его в GitHub Releases вместе с `.sha256`.

Сборку можно запустить и руками: **Actions → Release → Run workflow** → указать тег.

### Про подпись APK

Это самый частый вопрос, и у него есть развилка.

**Как обычно делают.** Есть два независимых пути, и их не смешивают:

1. **F-Droid.** Разработчик не присылает свой подписанный APK вообще. F-Droid
   берёт исходники из репозитория по указанному тегу, собирает у себя и подписывает
   **своим** ключом. Отсюда два условия:
   - сборка должна быть воспроизводима из исходников, без ваших личных ключей;
   - `versionCode` в `build.gradle.kts` должен расти монотонно — по нему F-Droid
     понимает, что это новая версия, а не дубль. Вручную следить не надо: обе
     версии F-Droid читает из Gradle-файла.

   Ключ разработчику для F-Droid не нужен вообще: подпись там всегда F-Droid-овская,
   и это нормально — пользователь ставит APK из репозитория F-Droid, а не ваш.

   При подаче F-Droid попросит метаданные (описание, категории, лицензия),
   скриншоты под три размера, `changelogs` по `versionCode` и работающую сборку
   из чистого клона. Готовый APK прикладывать не нужно.

2. **GitHub Releases / свой сайт.** Здесь вы раздаёте APK, и он должен быть подписан
   ключом, который **не меняется никогда**. Android устроен так: обновление
   принимается, только если подпись совпадает. Сменили ключ — на телефоне
   придётся удалить старое приложение (с его настройками) и ставить заново.

   Поэтому нужен один долгоживущий keystore. Ключ **не покупается и не выдаётся** —
   он генерируется на вашей машине один раз и больше никогда не меняется:
   ```bash
   keytool -genkeypair -v -keystore ebrake-release.jks -alias ebrake \
           -keyalg RSA -keysize 4096 -validity 10000
   ```
   На Windows `keytool` лежит в JDK Android Studio:
   `"C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe"`.
   Ключ **не коммитится** (в `.gitignore` уже есть `*.jks`, `keystore.properties`).
   Храните его в менеджере паролей и, если нужен CI, в GitHub Secrets.

**Что сделано в проекте.** Release-ключ создан и лежит вне репозитория
(в `%USERPROFILE%\keys\ebrake-release.jks`, пароль — в менеджере паролей).
`app/build.gradle.kts` умеет искать ключ в двух местах: `keystore.properties`
в корне (локально) или переменные окружения (в CI). Если ключа нет, release
собирается под debug-ключом — так релиз никогда не падает из-за отсутствия
секрета. Для настоящих релизов задайте `keystore.properties` или Secrets.

**Ловушка на Windows.** `keystore.properties` должен быть в кодировке **без BOM**,
иначе первый ключ прочитается как `﻿storeFile` и Gradle молча соберёт APK под
debug-подписью. Проверяется так:
```
<путь>\Sdk\build-tools\36.0.0\apksigner.bat verify --print-certs app\build\outputs\apk\release\app-release.apk
```
В `Signer #1 certificate DN` должно быть `CN=eBrake`, а не `CN=Android Debug`.

`ANDROID_KEYSTORE_BASE64` — это сам файл ключа, закодированный в base64:
```bash
base64 -w0 ebrake-release.jks
```
(Workflow сам распаковывает его во временный файл и подставляет путь
в `ANDROID_KEYSTORE_PATH` — вручную ничего настраивать не нужно.)

Локально (без CI) достаточно `keystore.properties` в корне проекта:
```properties
storeFile=/Users/you/keys/ebrake-release.jks
storePassword=…
keyAlias=ebrake
keyPassword=…
```

## Лицензия

**GPL-3.0.** Не потому что так модно: `x264` внутри ffmpeg — это GPL-код, поэтому
приложение, его распространяющее, обязано быть под GPL. Лицензия применима ко всему:
и к коду приложения, и к собранному AAR. Полный текст — [LICENSE](LICENSE).

Практическое следствие: исходники должны быть публично доступны (публичный
репозиторий это и обеспечивает), а в релизах нужно указывать, что распространяется
GPL-3.0.

## Ветки и публикация

Две ветки, обе живут на GitHub:

| Ветка | Для чего | Собирает CI |
|---|---|---|
| `dev` | вся разработка, сюда сливаются PR | debug APK + тесты |
| `release` | проверенное, только то, что можно отдавать пользователям | debug APK + тесты |

`main` не используется: так история релизов читается однозначно — всё, что в
`release`, уже было у пользователей.

```bash
# 1. Работаем в dev
git switch dev
git add -A && git commit -m "Релиз 0.1.0"

# 2. Ветка release = ровно то, что уедет пользователям
git switch -c release   # или git switch release
git merge dev
git push origin dev release

# 3. Тег — он и есть релиз. Workflow сам соберёт APK и опубликует его.
git tag -a v0.1.0 -m "eBrake 0.1.0"
git push origin release --follow-tags
```

Через 3–5 минут на странице репозитория появится раздел **Releases** с
`eBrake-0.1.0.apk`. Ссылка на него и есть то, что нужно давать пользователям.

Дальше цикл повторяется: изменения идут в `dev`, релиз — merge в `release` + тег.

Пуши в `dev` и `release` без тега собирают только debug (`build.yml`) — как проверка,
что ничего не сломалось.

Откат: тег удалить можно, уже собранный APK у пользователей останется. Поэтому
`versionCode` не переиспользуем — следующая версия всегда с большим числом.

## Архитектура

```
MainActivity
└── EbrakeApp                 Scaffold + HorizontalPager + FloatingDock
    ├── InputScreen           галерея, папка ввода, мультивыбор
    ├── EditScreen            сетка движков, сравнение качества
    └── OutputScreen          очередь, выполненные, лог

transcode/                    состояние и логика, UI о ней ничего не знает
├── TranscodeViewModel        один на все экраны
├── TranscodeQueue            источник правды: очередь, лог, выполненные
├── TranscodeService          фоновый цикл кодирования (переживает Activity)
├── TranscodeModels           движки, уровни, команды ffmpeg
├── EncoderCatalog            что есть в этой сборке ffmpeg
├── InputTarget / OutputTarget  папки ввода и вывода (SAF)
```

Ключевые решения и замеры качества — в [NOTES.md](NOTES.md), включая грабли
ffmpeg-kit (одноразовые SAF-URL, Kotlin-API вместо Java-описания) и то, почему
для MediaCodec используется VBR-таргет, а не `cq`.
